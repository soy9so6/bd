# NoSQL in Practice — Task Tracker

Учебный мини-проект для практического задания по использованию нереляционных баз данных.

## 1. Цель проекта

Показать практическое взаимодействие приложения сразу с тремя типами хранилищ:

- **PostgreSQL (реляционная БД)** — основное и надёжное хранение задач.
- **MongoDB (документоориентированная NoSQL БД)** — журнал событий аудита. События имеют JSON-подобную структуру, а набор полей может расширяться без изменения схемы таблиц.
- **Redis (ключ-значение NoSQL БД)** — кэш чтения задач с временем жизни ключа (TTL) 60 секунд.

Таким образом, проект не просто подключает NoSQL-хранилища, а использует их по назначению в рабочих сценариях.

## 2. Архитектура

```text
                 HTTP / REST
                     |
               FastAPI backend
                /     |      \
               /      |       \
        PostgreSQL  MongoDB   Redis
         tasks      audit     task:{id}
        (CRUD)     events     (cache, TTL)
```

### Сценарии взаимодействия

1. Создание задачи: запись в PostgreSQL, затем событие `task_created` записывается в MongoDB.
2. Чтение задачи: сначала проверяется Redis. При попадании возвращается кэш; при промахе данные читаются из PostgreSQL и помещаются в Redis на 60 секунд.
3. Изменение задачи: обновляется PostgreSQL, соответствующий ключ Redis удаляется, событие `task_updated` добавляется в MongoDB.
4. Удаление задачи: запись удаляется из PostgreSQL, кэш инвалидируется, событие `task_deleted` сохраняется в MongoDB.
5. Просмотр аудита: endpoint `/audit` читает документы непосредственно из MongoDB.
6. Статистика `/stats` агрегирует сведения из всех трёх хранилищ.

## 3. Запуск

Требуется установленный Docker и Docker Compose.

```bash
docker compose up --build
```

После запуска:
- API: http://localhost:8000
- Swagger UI: http://localhost:8000/docs
- OpenAPI: http://localhost:8000/openapi.json

Остановка:

```bash
docker compose down
```

Удаление контейнеров вместе с данными:

```bash
docker compose down -v
```

## 4. Проверка работы

Можно выполнять запросы через Swagger UI (`/docs`) или curl.

### Создать задачу

```bash
curl -X POST http://localhost:8000/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"Изучить MongoDB","description":"Проверить документную модель"}'
```

В ответе будет созданная задача с `id`.

### Получить задачу — первый запрос

```bash
curl http://localhost:8000/tasks/1
```

Ожидаемый признак: `"source": "PostgreSQL"`. Это промах кэша: данные получены из реляционной БД и помещены в Redis.

### Получить задачу — повторный запрос

```bash
curl http://localhost:8000/tasks/1
```

Ожидаемый признак: `"source": "Redis cache"`. Это демонстрирует чтение из NoSQL-кэша.

### Обновить задачу

```bash
curl -X PATCH http://localhost:8000/tasks/1 \
  -H "Content-Type: application/json" \
  -d '{"status":"in_progress"}'
```

После обновления ключ Redis удаляется. Следующий GET снова прочитает запись из PostgreSQL. В MongoDB появится `task_updated`.

### Посмотреть журнал событий MongoDB

```bash
curl http://localhost:8000/audit
```

### Посмотреть статистику

```bash
curl http://localhost:8000/stats
```

## 5. Что именно демонстрирует NoSQL

| Технология | Модель данных | Практическое применение | Преимущество в проекте |
|---|---|---|---|
| MongoDB | Документы BSON | История событий аудита | Гибкая структура событий, удобно хранить разные payload |
| Redis | Ключ-значение | Кэш задач | Быстрое повторное чтение, TTL, снижение нагрузки на PostgreSQL |
| PostgreSQL | Таблицы и связи | Основные задачи | Транзакционность и структурированные данные |

## 6. Вывод

В ходе работы создан REST-сервис управления задачами, использующий реляционную и две нереляционные базы данных. PostgreSQL выступает источником истины для бизнес-данных. MongoDB хранит историю действий в виде документов, а Redis ускоряет чтение часто запрашиваемых задач.

На практике реализованы запись и чтение документов MongoDB, операции с ключами Redis, установка TTL, проверка попадания в кэш и его инвалидация при изменении данных. Проект показывает, что нереляционные базы данных не обязательно заменяют реляционную: они могут дополнять её, решая специализированные задачи.

## 7. Ограничения учебной реализации

- Для простоты событие аудита записывается после фиксации транзакции PostgreSQL. В промышленной системе для гарантированной доставки событий стоит рассмотреть Transactional Outbox и повторные попытки.
- Redis используется как кэш, а не как единственное хранилище данных.
- Для учебного запуска сервисы MongoDB и Redis не имеют авторизации; не публикуйте такую конфигурацию в открытой production-среде.
- Временные метрики Redis являются общими метриками сервера, а не только данного приложения.
